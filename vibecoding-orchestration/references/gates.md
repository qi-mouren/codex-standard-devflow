# 门禁 G0-G5（gates.md）

## 总原则

产出的节点不能当自己的裁判。每道门禁由上级、独立评审或人类把关。形式检查可脚本化，内容判断留给人。

### Verification 证据要求（吸收自 agent-skills：验证不可妥协）

任何门禁判定（PASS / 驳回）必须有证据落盘，禁止"seems right"式结论：

- 测试类判定：附测试输出（通过/失败计数）、构建日志、运行数据，不含结论性日志的"应该没问题"不成立。
- 评审类判定：每个结论映射到具体产物（REQ 条目 / 契约接口 / 代码行），附引用路径。
- 驳回判定：附复现步骤或证据引用，禁止无依据的根因断言。
- 每个 PASS 项在检查表勾选时同步写证据位置（文件路径 + 行号 / 日志节）。

### 常见借口与反驳（吸收自 agent-skills anti-rationalization，防跳过步骤）

| 常见借口 | 反驳 |
|---|---|
| "这里改动太小，不用跑门禁" | 快速模式也要求独立评审不可免；小改动至少走 Task Gate |
| "测试都绿了，不用再人工验收" | 测试绿 ≠ 验收标准达成；G1 起的验收标准逐项人工/独立核对 |
| "风险是常识，不用写证据" | 风险/根因必须附证据或复现引用（见上 verification 要求） |
| "这个模块没暴露外部接口，不用契约登记" | 无跨模块接口也要在 LLD 显式声明"无对外接口"，防止下游误用 |
| "安全是上线后的事" | 涉及输入/认证/密钥/依赖的改动，G5 必查安全 lane（见下） |
| "先提交，评审之后再补" | 门禁是进入下一阶段的必要条件，非可选后补项 |
| "架构没问题，架构评审员走个形式" | G2 架构评审员必须独立产出 PASS/驳回报告，不得由架构负责人自评替代 |

## 门禁总表

| 门禁 | 位置 | 判定内容 | 控制者 | 形式 |
|---|---|---|---|---|
| G0 | 需求锚定 之后 | 需求完整、可测、无废案、无开放问题 | 人类（产品/客户） | 评审确认 |
| G1 | 产品需求 之后 | PRD 全量覆盖 REQ、验收标准可测 | 人类 PO + 总控负责人形式检查 | PRD 审阅 |
| G2 | 架构设计 之后 | 技术可行、风险可接受、覆盖全部 PRD | 人类架构师 + 架构评审员（必须 spawn 的独立子 agent） | 架构评审 |
| G3 | 模块拆解 之后 | 模块清单与 PRD 双向追踪、无遗漏越界 | 总控负责人（脚本化） | check-flow.ps1 |
| G4 | 详细设计 之后 | 契约交叉校验通过、归属唯一、无冲突 | 总控负责人 + 独立评审 + 人类签字 | 契约审查 |
| G5 | 开发实现之后 | 回归通过、验收标准全绿 | QA 评审员（必须 spawn，独立于开发） | 测试报告 + 发布决策 |

## 门禁分级（按轮次轻重，避免所有东西都走企业流程）

| 分级 | 适用轮次 | 门禁内容 |
|---|---|---|
| Task Gate | 快速模式小改动 | G-quick：任务书完成标准 + 独立评审记录 + 提交；不产 PRD/HLD/LLD |
| Module Gate | 标准/大型模式内的单个模块轮（LLD、开发） | 轻量：模块 LLD 形式校验 + 契约交叉校验 + 本模块单测/契约测试；总控或脚本执行，**不重复 G0-G3** |
| Epic Gate | 标准/大型模式的史诗级交付 | 完整 G0-G5：G0 人类、G1 人类+总控、G2 人类+架构评审员、G3 总控脚本化、G4 总控+独立评审+人类签字、G5 独立 QA |
| Milestone Gate | 大型模式里程碑发布 | 发布评审：范围+日期签字、全量回归、产品级汇总更新 |

规则：G4 契约冻结只在史诗级做一次，模块轮不重复 G0-G3；全量回归只在装配轮/G5 执行（dev 轮只跑本模块单测+契约测试）；自动判断模式可用 `scripts/node/classify-change.mjs`（建议非强制）。

## G0 需求评审检查表

- [ ] 每条 REQ 有唯一 ID（REQ-xxx）
- [ ] 每条 REQ 可测（有验收标准或可判定标准）
- [ ] 优先级已标注（MoSCoW）
- [ ] 无开放问题（未决问题已清零或显式挂起）
- [ ] 废案已归档并注明原因
- [ ] 需求锚点版本号正确
- [ ] 问题账（docs/agent/issues.md）无未分诊 open 或 Blocking 未决项

## G1 PRD 评审检查表

- [ ] PRD 覆盖全部 REQ（双向追踪可查）
- [ ] 每条需求有验收标准
- [ ] 无未决问题
- [ ] 追踪矩阵已更新（REQ ↔ PRD）

## G2 HLD 评审检查表

- [ ] 技术选型明确，有理由
- [ ] 覆盖全部 PRD（双向追踪可查）
- [ ] 风险清单完整，每个风险有缓解方案
- [ ] 架构师确认可行，未决项已列明
- [ ] 架构评审员子 agent 已 spawn 并产出独立评审报告（PASS/驳回）
- [ ] 评审驳回项已登记问题账（docs/agent/issues.md）
- [ ] 风险/结论类表述附证据或复现引用（禁止无依据的根因断言）

## G3 范围对照检查表（脚本可自动检查）

- [ ] 模块清单覆盖全部 PRD 功能点（无遗漏）
- [ ] 模块边界无重叠、无歧义（无越界）
- [ ] 模块数 3-8
- [ ] 每个模块有名称、职责、边界、依赖、验收入口
- [ ] 追踪矩阵已更新（PRD ↔ 模块）

## G4 契约冻结检查表

- [ ] 每个跨模块接口单一归属（契约注册表）
- [ ] 接口交叉校验通过（消费方与提供方一致）
- [ ] LLD 规范一致（命名、类型、错误处理）
- [ ] 人类架构师签字
- [ ] 打 tag：vX-contracts-frozen
- [ ] 契约仲裁遗留/未决项已登记问题账（docs/agent/issues.md）

## G5 集成/QA 检查表

**两阶段评审（吸收自 superpowers subagent-driven-development：先规格符合性、再代码质量）**

- 阶段一 规格符合性：实现逐条对照冻结契约 + REQ 验收标准，确认该做的都做了、没做越界的事
- 阶段二 代码质量：对阶段一通过的实现做五轴审查（见下），只有阶段一通过才进入阶段二
- 两阶段结论分开记录，任一阶段驳回即整条 G5 驳回（附理由与修订清单）

**五轴代码审查（吸收自 agent-skills code-review-and-quality）**

- [ ] 正确性：逻辑、边界、错误处理是否成立
- [ ] 可维护性：命名、结构、注释是否清晰；是否引入不必要的复杂度
- [ ] 性能与安全：明显性能退化；安全基线问题（见安全 lane）
- [ ] 测试覆盖：关键路径、边界、失败路径是否有测试证明
- [ ] 变更规模：单次变更是否过大（建议 ≤~100 行/次，过大则要求拆分）

严重级别标签（评审缺陷分诊用）：**Blocking**（必须修，阻塞发布）/ **Nit**（可修可不修）/ **Optional**（可选优化）/ **FYI**（知悉即可）。只有 Blocking 阻塞门禁通过。

**安全 lane（涉及输入校验、认证、密钥管理、依赖、外部边界的改动必查；吸收自 agent-skills security-and-hardening）**

- [ ] 输入校验：外部输入有边界校验，不信任用户输入
- [ ] 认证/授权：访问控制符合设计，无越权路径
- [ ] 密钥与机密：无硬编码密钥/口令，机密走配置/环境变量/密钥管理
- [ ] 依赖审计：新增/升级依赖做漏洞检查，无已知高危
- [ ] 三层边界：数据层/服务层/展示层边界清晰，最小权限原则
- [ ] 无 OWASP Top 10 高危项（注入、XSS、失效访问控制、敏感数据暴露等）

**G5 检查表**

- [ ] CI 编译通过
- [ ] 全部单测通过
- [ ] 契约测试通过
- [ ] 集成回归通过
- [ ] REQ 验收标准全部达成
- [ ] 缺陷已分诊：修复或显式延期（**延期缺陷必须登记问题账 deferred**，docs/agent/issues.md）
- [ ] QA 评审员子 agent 已 spawn 并产出 QA 报告（独立于开发）
- [ ] 缺陷根因附复现步骤或证据引用（禁止无依据的根因断言）
- [ ] QA 评审员已读取任务文件并复述任务，经总控确认
- [ ] 补验场景使用独立 task_name 新建验证 agent（如适用）
- [ ] UI 相关（启用 ui-design-intelligence 时）：视觉验收通过——对照 design-genome 评审截图，verdict=alive；含动效的 UI 还需 motion gate=pass（录屏/帧序列或 check-motion.ps1）
- [ ] 安全 lane（适用时）：上表安全项全部通过，结论附证据
- [ ] 问题账无未分诊 open 或 Blocking 未决项
