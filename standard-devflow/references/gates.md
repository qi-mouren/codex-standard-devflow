# 门禁 G0-G5（gates.md）

## 总原则

产出的节点不能当自己的裁判。每道门禁由上级、独立评审或人类把关。形式检查可脚本化，内容判断留给人。

## 门禁总表

| 门禁 | 位置 | 判定内容 | 控制者 | 形式 |
|---|---|---|---|---|
| G0 | 需求锚定 之后 | 需求完整、可测、无废案、无开放问题 | 人类（产品/客户） | 评审确认 |
| G1 | 产品需求 之后 | PRD 全量覆盖 REQ、验收标准可测 | 人类 PO + 总控负责人形式检查 | PRD 审阅 |
| G2 | 架构设计 之后 | 技术可行、风险可接受、覆盖全部 PRD | 人类架构师 + 架构评审员（必须 spawn 的独立子 agent） | 架构评审 |
| G3 | 模块拆解 之后 | 模块清单与 PRD 双向追踪、无遗漏越界 | 总控负责人（脚本化） | check-flow.ps1 |
| G4 | 详细设计 之后 | 契约交叉校验通过、归属唯一、无冲突 | 总控负责人 + 独立评审 + 人类签字 | 契约审查 |
| G5 | 开发实现之后 | 回归通过、验收标准全绿 | QA 评审员（必须 spawn，独立于开发） | 测试报告 + 发布决策 |

## G0 需求评审检查表

- [ ] 每条 REQ 有唯一 ID（REQ-xxx）
- [ ] 每条 REQ 可测（有验收标准或可判定标准）
- [ ] 优先级已标注（MoSCoW）
- [ ] 无开放问题（未决问题已清零或显式挂起）
- [ ] 废案已归档并注明原因
- [ ] 需求锚点版本号正确

## G1 PRD 评审检查表

- [ ] PRD 覆盖全部 REQ（双向追踪可查）
- [ ] 每条需求有验收标准
- [ ] 无未决问题
- [ ] 追踪矩阵已更新（REQ ↔ PRD）

## G2 HLD 评审检查表

- [ ] 技术选型明确，有理由
- [ ] 覆盖全部 PRD（双向追踪可查）
- [ ] 风险清单完整，每个风险有缓解方案
- [ ] 架构师确认可行，未决项已列明
- [ ] 架构评审员子 agent 已 spawn 并产出独立评审报告（PASS/驳回）

## G3 范围对照检查表（脚本可自动检查）

- [ ] 模块清单覆盖全部 PRD 功能点（无遗漏）
- [ ] 模块边界无重叠、无歧义（无越界）
- [ ] 模块数 3-8
- [ ] 每个模块有名称、职责、边界、依赖、验收入口
- [ ] 追踪矩阵已更新（PRD ↔ 模块）

## G4 契约冻结检查表

- [ ] 每个跨模块接口单一归属（契约注册表）
- [ ] 接口交叉校验通过（消费方与提供方一致）
- [ ] LLD 规范一致（命名、类型、错误处理）
- [ ] 人类架构师签字
- [ ] 打 tag：vX-contracts-frozen

## G5 集成/QA 检查表

- [ ] CI 编译通过
- [ ] 全部单测通过
- [ ] 契约测试通过
- [ ] 集成回归通过
- [ ] REQ 验收标准全部达成
- [ ] 缺陷已分诊：修复或显式延期
- [ ] QA 评审员子 agent 已 spawn 并产出 QA 报告（独立于开发）
- [ ] QA 评审员已复述任务并经总控确认
- [ ] 补验场景使用独立 task_name 新建验证 agent（如适用）

## 门禁结果记录

每个门禁的结果记录到 docs/process/STATE.md：

```
gates:
  g0: { status: PASS, by: 人类, date: yyyy-mm-dd, note: ... }
```

驳回记录格式：原因 + 回退目标版本 + 新版本号。
